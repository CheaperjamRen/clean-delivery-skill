# Clean Delivery

把交付面当成一个稳定接口。读者打开文件、看到标题、查看 diff、阅读普通问答或接收回报时，应当看到当前成果本身，以及完成判断所需的事实。

## 交付契约

1. 先在工作上下文里写清当前目标和停止条件。
2. 标题、文件名、章节名、注释、PR 标题和回报都使用任务本身的语言。
3. 交付内容包含最终结果、必要的验证信息、事实限制、阻塞项和可点击链接。
4. 草稿、候选路径、失败尝试和过程记录放在工作区或单独的审计记录里。
5. 用户给出新方向后，把新方向视为当前规格；旧方向的痕迹从交付面退出。

## 范围锁定

- 先复述当前成果和完成条件，再开始执行。
- 复用已有结构，采用能满足当前条件的最小改动。
- 额外想法进入待办或建议区，等待用户明确采纳。
- 验证、错误处理、抽象和文档保持与当前风险和请求相称。

## 各类交付物

### 注释

默认让代码自己说话。需要注释时，写一个读者无法从代码直接得到的理由、边界或失效条件。

### PR、Commit 和交付回报

先写最终行为，再写从 diff 无法看出的关键事实。测试命令、结果、风险和待处理阻塞项保持可核验、可定位、简短。

### 文档、报告、PPT 和文件

标题、文件名和目录名描述成果本身。正文按最终结构组织，段落服务读者当前要完成的事情。历史修订、删减轨迹和候选方案放入独立记录。

## 显眼的残留信号

- `去除某某版`、`按要求更新版`、`精简修订版 v2`
- `根据用户要求……`、`原计划……`、`已删除……`
- 注释里出现被否决方案、失败路径或未来设想
- PR 标题解释一个没有进入 diff 的功能
- 交付末尾出现未经请求的下一轮服务推销

看到这些信号时，回到当前目标、停止条件和最终状态，重新整理交付面。

## 需要保留的事实

干净交付保留真实限制：失败测试、未完成项、数据缺口、风险、权限要求和用户必须确认的动作。每一项用事实、影响和下一步动作表达；过程叙述留在独立记录。

## 交付前检查

- [ ] 标题和文件名读起来像成果本身。
- [ ] 正文没有候选路径、删改历史或自我辩护。
- [ ] 范围内的结果完整，范围外的想法已离开交付面。
- [ ] 验证结果、限制、风险和链接可核验。
- [ ] 用户打开文件即可开始使用或评审。

## 关键词

`干净交付`：最终状态优先。

`锁定范围`：在当前请求和停止条件处收束。

`只报结果`：回报按结果、证据、限制、链接排列。

`保留关键理由`：保留 non-obvious reason，删去过程性解释。

这些词需要出现在当前 Skill、AGENTS.md 或 prompt 中，跨会话记忆取决于宿主工具的实际配置。
